# Принципиальные решения (Практическая работа №6)

- **Фамилия, имя:** Серебрянников Матвей
- **Учебная группа:** ЭФБО-11-25
- **Дата выполнения:** 24.10.2026
- **Вариант:** 3 (`90 % 8 + 1 = 3`) — поведение срочной заявки, параметр `20` (`URGENT_MEDIUM_LIMIT_PERCENT = 20`: если заявка срочная и риск `MEDIUM`, то быстрый маршрут `FAST_TRACK` даётся только при сумме до 20% от фин. лимита, то есть `<= 100 000`, а выше идёт `STANDARD`).

## Решение 1. Порядок проверок if / else if от самого строгого правила к простому
Условия в задаче могут совпадать одновременно (например, заявка и срочная, и с персональными данными, и на большую сумму). Поэтому в методе `route` проверки расставлены строго по важности:
1. Персональные данные (`containsPersonalData`) -> `SECURITY_REVIEW`
2. Высокий риск (`risk == HIGH`) -> `DIRECTOR_REVIEW`
3. Сумма от 500 000 (`amount >= FINANCE_LIMIT`) -> `FINANCE_REVIEW`
4. Срочная заявка (`isEligibleForFastTrack`) -> `FAST_TRACK`
5. Все остальные случаи -> `STANDARD`

Из-за такого порядка срочность никогда не перекроет проверку безопасности или директора.

## Решение 2. Вынос проверок в отдельные методы и switch по уровню риска
Чтобы условие внутри `route` легко читалось, каждая проверка вынесена в небольшой вспомогательный метод, а проверка правила 3-го варианта для срочной заявки написана через `switch (risk)`. Если нужно поменять порог, правится только одна константа в `ApprovalRouter`.

## Результаты граничных проверок
1. **Точные границы суммы (`499999`, `500000`, `500001`):** `499999` (срочная, `LOW`) -> `FAST_TRACK`; `500000` -> `FINANCE_REVIEW`; `500001` -> `FINANCE_REVIEW`.
2. **Граница варианта 3 (`100000` и `100001` при `urgent=true, MEDIUM`):** `100000` -> `FAST_TRACK`, `100001` -> `STANDARD`.
3. **Конфликт всех признаков (`600000;true;HIGH;true`):** выдаёт `SECURITY_REVIEW`.
4. **Нулевая или отрицательная сумма (`0`, `-500`):** выбрасывает `IllegalArgumentException`.
5. **Пустой или неизвестный риск (`null`, `UNKNOWN`):** выбрасывает `IllegalArgumentException`.
